# 开发习惯与协作约定

本 skill 是用户的固定工程约定，跨所有项目生效。项目自身约定优先（见优先级第 1 条）。

## 用户画像

- 后端为主的全栈工程师。常用语言：Go、Rust（后端主力），TypeScript（前端），Python（脚本、数据处理与 AI 工具）。
- 编码习惯偏阿里系：遵循阿里巴巴 Go 编码规范的注释、命名与错误处理约定，gofmt 强制，配置外置；具体框架与技术栈随项目而定，不做跨项目假设。
- 风格画像：追新（新技术与最新稳定版依赖优先，版本号明确）；洁癖（零冗余、零死代码）；反冗余设计（反感无用抽象层、兜底分支和无意义默认值，错误该暴露就暴露）；单一路线（一个问题一个解决方案，只给一条推荐路线）；国际化（文档双语优先，文案与错误信息走 i18n 资源）；中文交流，先结论后展开，改动小而准，改完给出验证方式，不为炫技引入复杂抽象。

## 优先级

1. 项目自身约定永远优先于本指令：仓库 README / AGENTS.md / 项目级 Skill / 已有代码风格 / 依赖清单（go.mod、Cargo.toml、package.json）里实际使用的技术栈。
2. 本指令只规定做事方式、代码质量与工程形态，不规定技术栈与具体工具；不同项目可能选不同框架，不跨项目套用。
3. 不擅自引入新框架、新依赖或新技术栈；确有必要先说明理由并征求同意。

## 工具偏好

- 文件内容搜索一律优先用 rg（ripgrep）；确认环境里没有 rg 时才回落 grep。

## 做事方式

4. 先读后写：动手前先读目标文件及直接依赖（类型定义、配置、调用方、测试），以现有写法和目录结构为准。
5. 不臆造：不猜 API、路径、字段名、依赖名、配置项；查不到就明说不知道。
6. 非平凡改动先讲方案：1–3 句说明改什么、影响哪些文件、怎么验证；琐碎改动直接做。
7. 改动范围最小化：只动达成目标所必需的行，不顺手重构、不重排无关格式、不碰无关文件。
8. 范围之外发现死代码、重复逻辑、无用导出、注释掉的旧代码：指出来问我要不要清，不擅自扩大改动。
9. 改完必验证：跑构建、类型检查、lint 和相关测试再交付；跑不了就明说"未验证"及原因。
10. 诚实报告：分别写清成功、失败、跳过、未验证，不虚构运行结果。

## 代码质量（硬性）

11. 零冗余、零死代码：无用的函数、变量、import、配置项、注释掉的代码块，直接删而不是留。
12. 一个文件只干一件事：超出单一职责就拆文件；同一段逻辑出现两次就抽出来，第三次直接封装成独立模块。
13. 不加无用抽象：不要我没要求的接口、基类、工厂、配置项、feature flag、策略模式或预留扩展点。
14. 不写无用兜底：不要"以防万一"的空 catch、无意义默认值、重复校验、过度防御的错误吞掉；错误该暴露就暴露。
15. 一个问题一个解决方案：只给一条推荐路线，不并排摆多套方案让我挑。
16. 注释写"为什么"不写"做什么"；导出项和公共接口必须有文档注释；命名准确，不缩写、不用无意义词汇。
17. 禁魔法值：状态码、错误码、阈值、容量与批大小、重试次数、位标志、正则与字符集等字面量一律提取为命名常量或枚举，不裸写；0、1、-1、循环下标等自解释值除外。传输契约相关的字面量格式另按第 42–56 条执行。
18. 遵循目标语言社区规范与其格式化、静态检查工具链，交给工具自动格式化，报错清零再交付。
19. 错误处理按项目既有约定：包装时带上下文并保留原始错误链路，不用 panic 走业务流程。
20. 依赖策略：新增依赖选最新稳定版并注明版本；既有依赖不擅自升级。

## 工程形态（默认范式，可被项目覆盖）

21. 入口文件只装配不写业务：解析参数、调用启动装配、启动与退出。启动装配集中在一处，顺序即依赖顺序。
22. 一个文件一件事：文件控制在数百行内，超过约 300 行或开始承担第二职责就拆。
23. 重复代码用生成器消灭，不靠复制粘贴：新模块（控制器、服务、模型、类型、迁移、测试）一律由脚手架生成再改；生成器本身按"一个动作一个文件"组织；生成物必须改到可直接用，不留 TODO 空实现、不留未使用字段。
24. 分层按业务域再按职责：controller 与 service 同名同构，看目录就能定位对应关系。
25. 持久化模型与传输模型严格分离：数据库实体不作为接口出入参。
26. 基础设施按能力分包（响应封装、校验、分页、鉴权、客户端等），业务单向依赖基础设施，不允许反向依赖。
27. 横切关注点独立成包：路由注册、中间件各自独立，一个中间件一个文件，不混放。
28. 配置外置并按环境拆分，禁止硬编码地址、密钥、超时。
29. 数据库迁移按序编号，升级与回滚脚本成对，不留只有升级的迁移。
30. 交付物包含构建/任务脚本与容器化文件；热重载、代码覆盖率等其余工程设施按项目实际需要选配，不作统一要求。
31. 双语国际化优先：对外文档（README、接口说明、变更记录）同时提供中文与英文；面向用户的文案、错误信息、通知一律走 i18n 资源，不硬编码中文或英文；时间、货币、字符集、排序按 locale 处理。

## 交流方式

32. 中文回答；技术标识符、日志、报错原文保留不翻译。
33. 先结论后细节：先给结果和改动清单，再讲原理与取舍。
34. 不确定就标注假设与不确定点；引用外部事实附来源链接。
35. 不执行 commit / push / 发布 / 删数据 / 改 CI 等不可逆或对外可见操作，除非我明确要求。

## 历史项目沉淀的补充约定

以下条目提炼自过往项目的实际反馈，与上文冲突时以上文为准：

36. 要最好的方案，不要成本话术：方案讨论禁止按"最便宜/投入产出比"排序，不以工作量为由降级方案。产品未上线时不写兼容旧数据的回退分支、不做最小可用版本——兼容分支和临时实现是永久留在代码里的债；若真要分期，只讲技术依赖顺序。
37. 方案选机制根治，不选补丁：不接受"加个超时/重试/兜底先把问题挡住"式修复，先找机制性根因一次做对。对齐第三方或参照实现（竞品、开源标杆）时，先读它的源码提取真实规格（参数、交互、语义）再动手，不凭截图或印象猜。
38. 验证到"针对性测试全绿"为止：完成第 9 条要求的构建/类型检查/lint/相关测试即交付；用户没要求时不追加烟囱测试、GUI E2E、重复构建等额外验证轮次。对照实验类排查用户通常自己会做。
39. 不碰用户正在使用的真实环境：不自动操作用户在用的应用、窗口或账号（点击、移动鼠标、切会话、删会话）；用户自己开着 dev 会话或服务实例（dev server、开发中的应用等）时一律不可调试——CDP、computer-use 等任何自动化手段都不行，自动化调试只针对自己启动的实例；需要配合时（抓包、复现）写成清晰步骤清单交用户手动执行。自动化测试只针对自己创建的实例、会话与数据；清理只按自己创建时记录的 ID，绝不按标题/名称模糊匹配删除，绝不在用户活跃实例上并发跑自动化。
40. 交付后不盯流水线：push 触发 CI/发版后报告一句"已推送，流水线已触发"即收尾，不轮询监控；用户自己在 CI 网页看结果，只有被明确要求排查失败时才去看。
41. 改代码用编辑工具，不拿脚本批量替换：python 等脚本只做只读分析（数据统计、日志解码）；对源码文件的修改一律通过精确编辑完成——脚本盲改不可见、易切坏结构。

## 跨端传输约定（API / IPC 契约）

项目自身约定优先；本节是默认路线，不是可选项。

42. 传输字段（JSON key、query 参数、事件 payload）一律 camelCase；语言内部命名遵循各自社区规范（Rust 模块与函数 snake_case、类型 PascalCase；Go 按阿里规范大小写；TS 变量函数 camelCase、类型组件 PascalCase、文件 kebab-case），两端差异只允许在序列化边界一处消除。
43. 命名转换只允许用框架属性声明：Rust `#[serde(rename_all = "camelCase")]`、Go 结构体 `json` tag；禁止手写字段映射表和通用 snake↔camel 转换函数，也不允许为迁就一端把传输字段改成下划线。
44. 整型 ID 一律字符串：i64/u64 直传超过 JS Number 安全整数范围（2^53-1）会静默丢精度；序列化成 string，前端不再 parseInt。
45. 精确数值禁 float：金额、汇率用整数最小单位 + 单位/币种字段（`{ amount: 500, currency: "CNY" }`）；百分比用 0–100 数值，禁 `"50%"` 字符串。
46. 尺寸与时长只传基本单位整数：字节、毫秒、秒各自传整数；`"1.5 MB"`、`"03:24"` 这类可读格式只由前端展示层产出，传输层永远不出带单位的字符串。
47. 时间一律 UTC 毫秒时间戳（number）：禁字符串日期、禁秒级、禁本地时区时间戳；时刻字段命名 `xxxAt`，非毫秒单位的字段名必须带单位（timeoutMs、durationSeconds）；前端按 locale 格式化，后端不产出展示格式。
48. 布尔只传 `true`/`false`：禁 0/1 与 `"true"` 字符串；字段名带 is/has/can 语义前缀，禁反义命名（isDisable 之类）。
49. 枚举序列化为 string 字面量：禁数字枚举；TS 侧用 string literal union + zod `z.enum` 对齐；Rust 的 `rename_all` 管字段名不管枚举变体名，内部标签 enum（`tag`）的 tag 值要单独钉住；两端增删枚举值同一 commit 改。
50. 空列表返 `[]` 不返 `null`；`null` 只表示"明确没有"且必须在 schema 里显式声明（Rust `Option<T>` ↔ TS `T | null`），不许用 null 或缺字段表达空字符串和 0。
51. 请求参数区分"未传"与"零值"：Go 用指针、Rust 用 `Option` 且不加 `#[serde(default)]`（`default`/`omitempty` 只用于解析外部响应或读旧数据）——给新增请求字段兜底默认值会掩盖前端漏传。
52. 字典 key 一律字符串；有序数据一律数组，禁把 JSON 对象当数字索引列表用（TS 端对象 key 会变字符串，回 Rust/Go 还要再 parse）。
53. 契约两端同源且同步演进：serde 模型/struct 与 zod schema 是同一契约的两份手写副本，改一端同一 commit 改另一端；能用生成器（ts-rs、openapi codegen、protobuf）就不手写，项目已约定生成入口时优先走生成器；响应必须过 schema 校验再进 UI，禁 `as T` 裸转与 any——校验失败就是"后端改了签名"，必须立刻暴露，不许静默兜底。
54. 命令与事件命名分层固定：IPC 命令名 snake_case（对齐 Rust 函数名）；事件名 kebab-case 字符串常量，两端常量镜像（Rust `names` 模块 ↔ 前端 `EVENTS`），只改一端的静默失效要靠测试或注释钉住。
55. 参数与载荷一律用静态类型承载，禁裸 JSON/map 拼装：Rust 定义 `struct`（`Serialize`/`Deserialize`），Go 定义结构体 + `json` tag，TS 用 zod schema + `z.infer` 推导类型；`serde_json::json!`、`map[string]any`、对象字面量只允许出现在测试 fixture 与日志序列化，不允许作为 IPC payload、事件载荷、第三方请求体或查询参数的类型来源。
56. 前端禁 `any`：类型没写对就 `unknown` + 收窄，不许拿 `any`/`as any` 绕过编译检查，`@ts-ignore` 与无理由 `eslint-disable` 同禁；确实绕不开的第三方无类型面，局部声明类型或收窄后 cast 并在注释里写明为什么。此条由 ESLint 钉死（`@typescript-eslint/no-explicit-any` 及 `no-unsafe-*` 系列，配 type-aware 规则），报错清零再交付（第 18 条）。

## 日志与排查

57. 日志为排查服务：写关键路径时默认"出问题只能靠日志还原现场"，关键代码位置必须留日志——外部调用（HTTP/RPC/DB/缓存/队列/第三方 API）记目标、关键入参、耗时与结果；关键分支与决策点（降级、重试、fallback、限流与规则命中）记走了哪条路及依据；状态变更类写操作（创建/更新/删除）记操作主体、对象与关键结果；后台与异步任务（定时任务、消费者、goroutine/task）记开始、结束、耗时与失败原因。失败路径必须有日志且带上下文（错误本身 + 关键 ID/参数），禁止只有一句 "failed" 而看不出是谁、对什么、失败在哪一步。
58. 日志级别按固定语义选用，跨项目通用：error=本应成功但失败、需要人介入排查（请求处理失败、任务失败、数据写入失败）；warn=不符合预期但已自动处理或降级、值得留意（重试后成功、降级兜底、跳过脏数据、用量接近阈值）；info=关键业务动作与流程节点的常规留痕（服务启停、任务开始与结束、外部调用概要、状态变更）；debug=排查所需的详细中间状态（完整出入参、分支判定依据），生产默认关闭。禁拿 error 打可自愈的事，禁把失败只记成 info/debug。
59. 错误日志只打一次：在错误最终处理处（暴露给调用方或顶层兜底处）带完整上下文记录；中间层只包装错误不重复打印，已向上返回的错误不再由当前层打 error，禁同一错误层层刷屏。
60. 日志用结构化字段不拼字符串，key 风格与传输契约一致；敏感信息（密钥、token、密码、证件号）不落日志，必须输出时脱敏。调试残留（console.log、println!、dbg!、fmt.Println、print）交付前清零；排查期间加的临时日志交付前删除或转正为正式日志。
61. 排查三板斧：先读完整报错——堆栈与错误链逐层读完，不凭最后一行猜；复现先收敛到最小复现路径；定位按"读日志 → 加临时日志或断点 → 二分缩小范围"推进，找到机制性根因再修（对齐第 37 条）。
